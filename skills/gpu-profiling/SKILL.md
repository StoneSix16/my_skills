# GPU 推理性能剖析

三个目的，一条主线：

1. **了解程序的计算流程** —— 谁调谁、算在什么形状上、稳态是什么
2. **分析性能瓶颈** —— 把「慢」归因到具体的阶段、算子、原因
3. **由浅入深地了解计算细节** —— 分层下钻的过程本身就是读代码的路径

三者是同一件事的三个尺度：要归因必须先把流程摊开，摊开流程的过程就是理解细节的过程。所以本 skill 的骨架是**分层**，不是「优化」。

**范围**：只负责测量、归因与流程梳理。优化方案单独立项——先测量清楚再谈优化，否则改的是猜出来的瓶颈。

## 测量方向：先选对手段

| 方向 | 回答什么问题 | 手段 | 产出 | 参考 |
| :--- | :--- | :--- | :--- | :--- |
| 流程踏勘 | 程序是怎么算的 | 读本地文档与代码，**不跑程序** | 调用链 + 计算单元清单 | 阶段 0 |
| 分层计时 | 时间花在哪一段 | 边界打点，CUDA Event + `perf_counter` 双计时 | 各层 self/inclusive 耗时表 + 未归因项 | 阶段 2–3 |
| 形状普查 | 算在什么形状上、稳态是什么 | 包裹子模块，只读 `(shape, dtype)` 与调用次数 | 形状清单 + 不变性判据 + 池占用曲线 | [measurement.md](references/measurement.md) |
| 算子区间统计 | GPU 时间归到哪个代码单元 | NVTX 区间 + nsys 归因 | 区间树 + 每区间 kernel 时长与次数 | 阶段 2–3、[nsys-usage.md](references/nsys-usage.md) |
| 计算量分析 | 这个算子是算力受限还是带宽受限 | 由形状推 FLOPs / bytes / AI，与本机比值相比 | 算量-访存-强度表 | 阶段 5、[measurement.md](references/measurement.md) |
| 空闲归因 | GPU 为什么没跑满 | 窗口并集 + 同流空隙 + 后继 kernel 分类 | 空闲构成 + 成因（下发受限 / 停滞） | 阶段 4、[idle-attribution.md](references/idle-attribution.md) |
| 对照实验 | 这个改动真的生效、真的更快吗 | 同口径重复采样，比统计量与波动 | 时间差 + 它是否大于运行间波动 | 阶段 6 |

「算子区间统计」还有第二种聚合：**按 kernel 族汇总时长排行**（框架搬运、GEMM、gather、norm…）。它共用同一次采集，独立价值在于兜住 **NVTX 区间没盖到的算子**——落进父区间、事后无法按代码单元归因的那部分开销，只能靠这一项现形。

**怎么选。** 问题决定方向，不是反过来：

- 说「慢」→ 分层计时；说「GPU 利用率低」→ 空闲归因；说「这个算子贵不贵、能不能优化」→ 计算量分析。
- **先分层，后算子**。没有 L1 先告诉你「哪 3 个阶段占了 98%」，算子报告只会又大又碎，你会盯着一堆无关 kernel。
- **一次采集喂多个方向**。算子区间统计、kernel 族汇总、空闲归因共用同一次 nsys 采集——所以**区间怎么划必须在采集前定**，它取决于阶段 0 的流程图。
- **算量占比不是时间占比**。两者经常对不上——实测见过算量只有别人 40% 的负载吃掉 90% 的时间，原因是它带宽受限且算子更小。**两者必须并排呈现，差距本身就是结论**。

## 阶段 0：先读懂流程，再定计划

不做假设，先测绘。前两件必做，第三件有疑点才做。

### 0.1 读流程

优先读项目本地文档（架构、调用链），缺口再用代码补。四样产出，缺一样都别开采集：

- **调用链**：入口 → 调度/预处理 → 前向 → 计算单元 → 子层
- **计算单元清单**：多少个 block、多少个分片单元、循环跑几步——它决定 L1 打在哪、L2 区间划在哪
- **路径清单**：同一份代码跑不同形状或不同步数时，多条执行路径要分开命名
- **形状与稳态**：输入输出形状、cache 何时填满

**流程没抄清楚之前不要采集**：区间划在哪、打点打在哪、按什么标签分流，全都取决于这张图。

### 0.2 把问题翻译成测量计划

照上节的目录选 1–2 个方向，落成一份计划：测哪一层、在哪些边界打点、贴什么标签、采哪些形状、跑几次、稳态怎么判定。

写不出「这个数的期望量级」的计划先别执行——那是采集，不是测量。

### 0.3 有疑点才建验证靶子表

用户点出的怀疑、或读代码时发现的「这看起来不对」，才写进去。

**不要为了凑数自己编候选热点**：RoPE 的 fp64、每步一次 `empty_cache`、dtype 转换这类直觉候选，实测常只占零点几个百分点；而真正的大头（框架的分片搬运、host 侧准备）不读流程根本想不到。

| 列 | 要求 |
| :--- | :--- |
| 疑点 | 写成能被测量推翻的命题 |
| 观察方式 | 用什么 kernel 名 / 哪个区间 / 哪个计数去筛。**写不出的删掉**；采集前就写好，不是事后补 |
| 裁决 | 测完回填：证实 / 证伪 / 未做对照 |

这张表是后续所有结论的索引。

## 阶段 1：定口径

**量化结论必须带测试条件**，否则下次无法比对。开工前写下来：

- 硬件与卡数（单卡/多卡的结论**不可互推**——`all-gather` 在单卡下退化为本地拷贝，占比完全不同）
- **实现版本**。特别注意「配置文件写了 A、代码里显式传了 B」这类覆盖：实测遇到过配置文件里改参数完全不生效，因为调用点硬编码了 kwarg
- 采样范围（只测了 32 层里的第 0 层，就必须写明）

### 稳态判据

非稳态有两种，**出现哪一种都要写进口径卡**——不是排除掉就当没发生过：

1. **冷启动**：cache / 滑动窗口 / 编译产物还没填满。有这类负载时先跑够再测，否则测到的是启动过程。
2. **测量窗口内的漂移**：同一算子的延迟随迭代单调变化。最典型的是 KV cache 增长——占用涨上去之后，同一个 `attn1` 在窗口末尾比开头慢，于是「整段的均值」不对应任何一个真实的单次调用。

判据：把指标**按步分桶**画一条曲线，看它是平的还是斜的。形状普查记录的池占用曲线就是这条判据的输入——占用还在爬，延迟就还在爬。

漂移**不禁止**用均值，禁的是不带范围的均值：

- 报「第 N 步」的单步值，或分桶后的区间。
- 报均值时写成「第 3–10 步的均值」，**让范围随数字一起出现**。范围不写的均值等于没测。
- 口径卡里写明选了哪一段、依据是什么（哪一步起曲线变平）。

### 测量入口

**真实 workload 优先**：直接在真实入口（真实请求 / episode / 真实数据）上测，测到的就是线上行为。

只有需要控制变量时才另写一个**最小复现脚本**（固定输入、固定形状、固定步数，把被测的计算单元单独拎出来跑），典型用途是扫描某个形状、或对比两种实现。代价是它绕过了真实调用路径（cache 管理、调度、动态 batching），结论**必须回到真实 workload 上复核**。

写下一张口径卡，**每张表都标它出自哪次运行**。

## 展示纪律：每个数字都要能自证所指

看到这个数的人必须能说出**它在哪个对象、哪一段范围上量的**。做不到，它就不是结论。

**标对象与范围。** 「`attn1` 耗时 0.264 ms」不合格——单次调用、单个 block、单步、还是整个 episode 的均值？写成「`attn1` 单次调用（中位）」、「`fwd_action_denoise` 单步」、「整个 episode（300 步）」。范围会因漂移而改变含义，所以范围必须和数字写在一起（见上节）。

**百分比必须给分母。** 「占 34.1%」不给分母，读者既无法验证，也无法与别的百分比相加。分母要么是同口径的总量（如「占 kernel 总时长 3516.4 ms」），要么写在表头。

**能不用百分比就不用。** 绝对量加一个总量，比一串百分比有用：百分比会掩盖绝对量——「占 90%」的可能是 1 毫秒。只有当「占比」本身就是结论时才用（覆盖率、空闲率）。

**跨运行比较只用稳定的那一类。** 数字分两类，行为不同：

| 类别 | 行为 | 例 |
| :--- | :--- | :--- |
| **kernel 归因类**：kernel 总时长、各 kernel 族的时长与次数 | **稳定**，可跨运行比较 | 总时长、某 kernel 命中次数 |
| **span 类**：区间跨度、墙钟、空闲率 | **随运行浮动**（实测 ±3%），只在单次运行内自洽 | `Proj Time`、`Range Time` |

拿 span 类数字做跨运行对比，会得出不存在的「性能变化」；引用它时必须带上出处。

## 阶段 2–3：分层测量（计时 + 算子区间）

两级，逐级下钻。**每级都要有可自证的覆盖率**，否则你只是在看一堆漂亮的数字。

两种手段**都能给出不越界的结果**，但「不越界」的原因不同：

| 手段 | 为什么准确 | 需要什么同步 |
| :--- | :--- | :--- |
| CUDA Event（L1） | 事件是**流内有序**的标记：区间的 kernel 排在起止事件之间，GPU 过起点之后、过终点之前执行的必然是这段计算 | 只在**读取**结果前同步一次，边界不需要 |
| nsys 按发起时刻归因（L2） | `correlationId` 把 kernel 连回**发起它的那次调用**，与它何时在 GPU 上执行无关 | 不需要。同步对归因没有影响，只会改变被测对象 |

**只有一种做法会越界**：拿 CPU 的时间窗口去框 GPU 的执行，也就是用它**归因**。它不是「同步不够」，而是口径本身错——详见 L2。（窗口本身不是禁忌：用窗口回答「这段时间 GPU 忙不忙」是合法的，那是空闲归因的第一步。）

**默认要求不越界**：任何一次测量若只能给近似值（越界、只覆盖部分 stream、只采了一个 block），必须写进口径卡，不能混进结论。

### 探针怎么放（L1、L2 共用）

三种落法，**按侵入性从小到大选**，前一种能解决就不用后一种：

| 落法 | 代价 | 用在哪 |
| :--- | :--- | :--- |
| **外部包装**：替换或包裹方法，不改方法体 | 补丁独立成文件，可整体摘除 | 默认 |
| **源码内插桩** | 污染业务代码 | 观察点在被调用的方法内部，从外面裹不到 |
| **复制方法体手动插桩** | 副本会与原始实现脱节 | 只能观察局部闭包、内联表达式、一串算子时 |

**两条硬要求：**

- **关掉后零开销，且能整体摘除**。开关不生效时探针不能再执行——热点路径上留一个 `if` 也算开销。编译型用条件编译，解释型用环境变量做一次性分支。
- **按能否常开分两类**：只读元数据的（形状、调用次数、池占用）可以常开；改变时序的（NVTX 区间、栈记录式 profiler、插在热点路径上的计时）只能短时开——后者常开，测到的就不是原来的负载了。

走第三种落法时，跑的是**副本而不是原始代码**；原始实现一改，副本不会跟着改，于是 profiling 描述的是一个不再存在的实现——而且通常不报错，只是悄悄少了一个分支。所以必须把「**副本 vs 当前原始实现**」的**逐句差异**打印成一条**可运行的检查**，而不是靠自觉。

### L1 粗粒度层（CPU 时钟 / CUDA Event）

用 CPU 时钟或 CUDA Event 测「一段时间」。**测量对象随项目而定**，常见的有：

- **整段**：整个 episode、整个请求的墙钟
- **单步**：单个 chunk、单次迭代、单次前向
- **阶段**：预处理 / 前向 / 后处理 / 通信 / 落盘
- **组件**：被调用的各个子模块

在**边界**打点，记录每次调用的 `(标签, cuda_ms, wall_ms)`。

判据：打点覆盖 ≥95% 的目标时间，剩余显式标为「未归因」。

跨进程或跨机器的边界用同一套办法，只是打点位置换成对端：对端没有代码可控时，用落盘文件或日志的时间戳（如 `st_mtime_ns`）近似，判据同样是各段之和与总墙钟的误差 < 5%。

要点：

- **双计时**。CUDA Event 给 GPU 执行时间，不必每调用同步；`perf_counter` 给 CPU 入队时间。只记前者会把不产生 kernel 的阶段（分配器 flush、纯 Python 重排）报成 0；只记后者会把 GPU-bound 阶段报成入队开销。两者之差直接说明该阶段偏向哪一边。
- **同步只在读取前做一次**。`cudaEventElapsedTime` 要求两端都已完成，否则返回未就绪。除此之外不要在边界同步——那会清空队列、破坏重叠、拉长墙钟，测到的已不是原来那个负载。
- **`cuda_ms` 是跨度，不是 kernel 之和**。它覆盖起止事件之间的整段 GPU 时间，中间的 GPU 空闲、别的流插进来的工作都算在里面。问「这段计算用掉多少」要另算。
- **事件是逐流的**。只给主流记一对事件，落在其他流上的工作（框架的拷贝流、通信流）不进这个数。要么在涉及的每条流上都记一对，要么在口径卡里写明「只覆盖主流」。
- **分层标签**。方法在另一方法运行期间被调用时记录斜杠连接路径（`infer/fwd_video_denoise`），层级关系就自带在名字里。
- **多条执行路径分开统计**。同一份代码按输入或配置走不同分支时（不同形状、不同步数、不同模式），各分支的耗时构成往往完全不同，合并成一个总的「阶段耗时」会失去意义——你会得到一个谁都不对应的平均值。给每次调用按路径打标签，统计时分开。
- **条目是 inclusive 的**。父条目的时间已含子条目，按列求和必然重复计算——必须重建调用树、报告 self 时间。**自校验：所有 self 时间之和恒等于根节点的 inclusive**。
- 在**边界**打点而非在循环体插桩：包裹被调用的方法并按参数打标签，就不需要改动循环本身。

### L2 算子层（NVTX + nsys）

NVTX 区间 + `nsys`。工具的具体用法、失败判据、CSV 陷阱见 [references/nsys-usage.md](references/nsys-usage.md)。

**先对齐边界。** 区间的边界要与**计算单元的边界**对齐，这一条决定了能回答什么问题。把区间划在框架的分片单元上（如 `attn`/`ffn`/block），就能用「区间时间」与「参数搬运时间」相减，得到搬运的代价——这是 L1 的粒度做不到的。对齐错了，只能得到一堆无法归因的总数。

归因的规则**只有一条**：

> 每个 kernel，归给「**发起它的那个 CPU 时刻**」在「**它所在线程**」上所处的**最内层区间**。

落成三步：

1. kernel 表 → `correlationId` → `CUPTI_ACTIVITY_KIND_RUNTIME`：拿到发起这次 kernel 的 `globalTid` 与 CPU 时刻
2. 在该线程的区间表里，找包含这个时刻的最内层区间
3. 把该 kernel 的时长计入这个区间

**自校验。** 每个 kernel 只归一次，所以合计**精确等于 kernel 总时长**，无未匹配项。对不上就是规则用错了，而报告看起来仍然自洽、只是所有占比都偏小——这是唯一能自动发现它的办法。

**不要用 CPU 窗口归因**（「kernel 在 GPU 上执行的时刻落在区间的 CPU 括号内」）。它看似与发起时刻等价，其实不是：括号不是流里的标记，两者之间不存在有序关系。CPU 提前入队、领先量可以到一整个队列，所以越界只发生在**区间短于它面前的积压**时——实测同一份报告里，`ffn`（括号 150 µs、积压 262 µs）越界率 100%，`attn1`（696 µs、5 µs）0%。它诱人是因为 GUI 上 NVTX 条看着就压在 kernel 条上面，但那是「GPU 跑它时 CPU 在哪」，不是归属（见 [nsys-usage.md](references/nsys-usage.md) 的「读 timeline」）。用同步去对齐也不可取：那改变了被测对象。

**代价要认清**：按发起时刻归因，得到的是「这段代码**发起了**多少 GPU 工作」，不是「这段时间 GPU **在干什么**」。后者要按 GPU 时间轴切分（见阶段 4）。两者别混用——`Proj Time` 这类跨度不可相加，正是因为不同区间的 GPU 跨度会互相重叠。

**另外两点：**

- **按执行路径拆分时要取整个区间栈**，不能只看最内层——区分路径的那个区间在栈中间，最内层是它们共用的子模块名。
- **父区间直属不等于某一类开销**。它装的是「没有单独打点的那一层计算」+「框架开销」两样东西，整体当成后者会系统性高估。

## 阶段 4：GPU 空闲归因

**当 L2 显示 GPU 空闲显著时做这一步**。流程见 [references/idle-attribution.md](references/idle-attribution.md)，脚本见 [scripts/nsys_attr.py](scripts/nsys_attr.py)。

核心是把「有停顿」变成「停顿在等谁」——两者的缓解手段完全不同。六步的骨架：

1. 区间窗口取**并集**，看窗口内有没有任何 kernel 在跑 → 真正空闲（**求和口径会因区间重叠而失真**）。这一步问的是「GPU 忙不忙」，不是「kernel 算谁的」——窗口在这里合法，在归因里非法（见 L2）
2. 每实例取**自己 kernel 的 GPU 跨度** vs 忙时 → 该单元自身的效率
3. 只看**同 stream** 的相邻 kernel 空隙 → 排除跨流交织
4. 按**前驱 kernel 时长**分组看空隙 → 分离固定调度开销与停滞
5. 按**后继 kernel** 分类长停顿 → 定位成因
6. **kernel 时长分布**（中位、短 kernel 占比）→ 判断是否下发受限

判据与常见结论：

- 空闲率**必须落在 [0, 100%]**。算出负数说明单位不一致（多半是拿 CPU 括号的跨度对了 GPU 的忙时）。
- 一个单元空闲是否严重，看的是**它的算子粒度**，不是它的算量。几十个平均几微秒的 kernel 会让调度开销大于计算本身；四五个大 kernel 则能把间隙盖住。
- **全局空闲的大头往往不在你以为的模块里**。实测中某个「看起来最重」的模块空闲 62%，而全局空闲的 94% 落在更外层的框架胶水里。
- **同步点是显式停顿源**。`synchronize()`、`.item()`、`.cpu()` 会把队列排空，让之前排队的全部工作串行地暴露出来，表现为一个极长的停顿。它**后面**的第一个 kernel 通常与原因无关，别按它归因。

## 阶段 5：计算量分析（算量与算术强度）

见 [references/measurement.md](references/measurement.md)。三条要点：

- **形状普查代替 FLOPs 计数器**。只读张量的 shape 与 dtype，不碰数值，可以在真实 workload 上常开；而基于栈记录的 profiler 会把前向撑大约 1.6×（单次实测，只作量级参考，不是通用系数）。
- **算术强度必须带硬件参照**。`FLOP / byte` 本身没有判据意义，要与本机的 `峰值算力 / 显存带宽` 相比。没有这个比值，「AI = 219」既不能说明算力受限也不能说明带宽受限。
- **注意哪些算子没有进统计**。pool gather、逐元素链、参数搬运都不产生 FLOPs，占比不能直接当作时间占比。

## 阶段 6：对照实验

两个条件各测一遍、比时间差，看上去直接，但**单次对比不足以下结论**——一次运行的差异可能全部来自噪声。

只有需要**证明因果**时才做这一步：「改了之后真的更快吗」。

**怎么测：**

- 同一条件**重复 N 次**（至少 5 次，噪声大就 10 次），并**丢掉预热轮**。
- 只比**稳定量**（kernel 归因类），span 类作辅证（见「展示纪律」）。
- 各条件必须**同一口径**：同一硬件、同一稳态窗口、同一进程配置。

**怎么判：** 差异必须**大于运行间波动**。小于波动就写「没有观察到差异」，不要报方向。

**两条约束：**

- **一次只改一处**。批量改完之后，即使变快了也不知道是哪一处的功劳，变慢了更不知道该回退哪个。
- **必要时放大信号**：造一个把目标瓶颈放大的场景（更长的主序列、更大的 batch、关掉其它阶段），让差异抬到噪声之上。

## 阶段 7：归档

三类内容分开存放，否则文档会同时变成规格、教程和实验记录：

| 文档 | 回答 | 内容 |
| :--- | :--- | :--- |
| spec | **要测什么** | 目标、约束、技术选择与理由、任务分解、验收标准。不写任何测量数值 |
| guide | **怎么测** | 工具用法、命令、失败判据、读数陷阱 |
| results | **测到了什么** | 所有数值，每张表标注出自哪次运行与适用范围 |

另外：

- 数值的写法遵守「展示纪律」：标清对象与范围，百分比给分母，跨运行只比稳定量。
- 工具入库，测量产物不入库。
- **未验证事项清单要随验证进展更新，不能只增不减**。一条被证伪的旧结论留在清单里，比没有清单更糟。
- 结论分「已失效」与「未验证」两类。实现一变（换了 attention 后端、换了精度），受影响的实测列要显式标记失效，而不是悄悄留着。

## 反模式速查

| 反模式 | 后果 |
| :--- | :--- |
| 没搞清流程就开采集 | 区间划错，只能得到一堆无法归因的总数 |
| 凭直觉编候选热点 | 精力花在只占零点几个百分点的算子上 |
| 跳过 L1 直接做算子级 | 报告巨大且无法归因 |
| 把多条执行路径合并统计 | 得到一个谁都不对应的平均值 |
| 在冷启动（cache 未填满）时测量 | 测到的是启动过程 |
| 对窗口内还在漂移的指标取均值 | 报出一个谁都不对应的数 |
| 用 span 类数字做跨运行对比 | 得出不存在的性能变化 |
| 对照实验只跑一次 | 差异可能全部来自噪声 |
| 探针没有可关闭的开关 | 长期带着它跑，测到的不是原来的负载 |
| 按 kernel 起始时刻落窗归因 | 短区间被数成 0 |
| 用同步去对齐窗口口径 | 改变了被测对象，测到的已不是原来那个负载 |
| 按执行路径归因只看最内层 | 判不出路径归属 |
| 把父区间直属整体当作某类开销 | 系统性高估该开销 |
| 跨嵌套区间相加区间时间 | 重复计数（那是跨度不是和） |
| 算术强度不带硬件参照 | 无法判定 compute- 还是 memory-bound |
| 混用 CPU 与 GPU 时间口径 | 出现负的空闲率 |
