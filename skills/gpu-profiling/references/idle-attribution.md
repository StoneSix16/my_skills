# GPU 空闲归因

当 L2 显示「GPU 空闲显著」时，用它把「有停顿」变成「停顿在等谁」。六步，每步回答一个不同的问题；跳过任何一步都会把结论引向错误的缓解手段。

所有查询都能在 `nsys` 导出的 sqlite 上跑：

```
nsys export --type sqlite -o db.sqlite <report>.nsys-rep
```

或直接用 `scripts/nsys_attr.py`（封装了同样的逻辑，带自校验）：

```
python scripts/nsys_attr.py <report> --idle --gaps [--idle-match SUBSTR] [--top N]
```

一次跑完第 1–5 步：`--idle` 出第 1、2 步的表（每个区间的窗口并集 / 忙时 / 空闲），`--gaps` 出第 3、4、5 步（按 stream 的空隙、按前驱时长分组的空隙中位、长停顿的后继 kernel 分类，以及长停顿落在哪两个区间之间）。自校验若报 `MISMATCH`，后面的占比全部不可信，先修归因规则。

## 两张表，先认清

- `CUPTI_ACTIVITY_KIND_KERNEL` —— `start` / `end` 是 kernel 在 **GPU 上**的执行区间（同一时钟，纳秒）
- `CUPTI_ACTIVITY_KIND_RUNTIME` —— `start` 是**发起**这次 kernel 的 CPU 时刻，还带 `globalTid`。把 kernel 连到发起它的线程与时刻，靠 `correlationId`
- `NVTX_EVENTS` —— 区间。名字可能落在 `text`，也可能落在 `textId`（要 join `StringIds`）。两列都看，否则会整批漏掉框架自己发的区间

## 第 1 步：真正空闲是多少

**问题**：窗口内有没有任何 kernel 在跑？

**做法**：取该区间全部实例的 CPU 括号，**合并成并集**；再取全部 kernel 的并集；求交。

```python
def merged(rows):           # rows of (start, end)
    out = []
    for s, e in sorted(rows):
        if out and s <= out[-1][1]:
            out[-1][1] = max(out[-1][1], e)
        else:
            out.append([s, e])
    return out
```

**为什么取并集**：同线程、同名的区间实例是**栈式嵌套**的，必然互不重叠（实测三个区间，时长之和与并集逐位相同）；会重叠的是**跨线程**统计，或把嵌套的多层混在一起算。并集在不重叠时退化为求和、重叠时自动去重，所以一律用它。求和导致重复计数是本步最容易犯的错。

**这一步用窗口是合法的**——它问的是「这段时间 GPU 忙不忙」。窗口的非法用法是另一件事：拿它把一个 kernel 算给某个区间（见 SKILL.md 的 L2）。两者别混。

结论读法：并集窗口 = 「这个单元的括号开着的那段时间」；并集内的 kernel 并集 = 「那段时间里 GPU 确实在干活的时长」；差 = 真正空闲。

## 第 2 步：这个单元自身有多忙

**问题**：在它自己的 GPU 跨度里，有多少时间是在跑它自己的 kernel？

**做法**：对每个区间实例，取归属它的 kernel（用 L2 的投影规则），算 `max(end) - min(start)` 作为跨度、`sum(end - start)` 作为忙时。

```
空闲占比 = 1 - sum(durations) / (max(end) - min(start))
```

**口径警告**：这里的「跨度」必须是 **kernel 的 GPU 跨度**，不能是 NVTX 区间的 CPU 括号。两者混用会得到**负的空闲占比**——CPU 括号比 GPU 执行还短（CPU 跑在 GPU 前面是常态）。负值一出现，先检查单位。

**结论读法**：这一步衡量的是「这个单元自己的 kernel 之间有多少缝」，与第 1 步不同。第 1 步问「GPU 闲着吗」，这一步问「这段忙碌里有多少是它自己造成的」。

## 第 3 步：排除跨流交织

**问题**：第 2 步看到的缝，是真空闲还是被别的 stream 填了？

**做法**：只统计**同一 `streamId`** 上相邻 kernel 的空隙。

```
gap_i = max(0, start_{i+1} - end_i)，i 与 i+1 在同一 streamId
```

按 stream 分别汇总「跨度 / 忙时 / 同流空隙」。在多 stream 的负载里（框架的分片搬运、通信通常有自己的 stream），主 stream 的空隙率会明显高于全局空闲率——两个数都要看：全局空闲说明 GPU 闲，同流空隙说明**这条流的依赖链**没排满。

## 第 4 步：分离调度开销与停滞

**问题**：空隙是「每个 kernel 的固定开销」还是「某处卡住了」？

**做法**：按**前驱 kernel 的时长**给空隙分组，看各组的中位空隙。

实测的典型形态（单项目单卡，两档数只作量级参照，值得记住这个形状）：

| 前驱 kernel 时长 | 空隙中位 |
| ---: | ---: |
| < 5 µs | 6.1–6.5 µs |
| > 5 µs | 2.2–2.4 µs |

读法：
- **长前驱时的 2.2–2.4 µs 是每 kernel 的固定调度下限**（grid 建立 + 退场）。这个数不会因为你少启动几次而改变。
- **短前驱时多出来的那 4 µs**——前驱还没退场完，下一个就开始不了。**前驱越长，这份开销越能被摊掉。**

所以「kernel 时长分布」直接决定上限：

| 中位 kernel 时长 | 判断 |
| :--- | :--- |
| 明显大于调度下限（数十 µs） | 计算/带宽受限，间隙不是问题 |
| 与调度下限同量级（几 µs） | **下发受限**，GPU 一半以上时间在等调度 |

## 第 5 步：定位长停顿的成因

**问题**：那些远大于调度下限的停顿（阈值取 200 µs 起）在等什么？

**做法**：按**后继 kernel 的类别**给长停顿分组。

```
对每个 gap > 阈值:
    记下它的后继 kernel 名，归到一个类别
按类别汇总 gap 的时长与个数
```

这一步是整节里最有价值的：它把「有停顿」变成「停顿在某类操作之前」。

实测的一个形态：投影到 `fwd_*` 区间内的长停顿，**99.8%** 紧挨着参数 all-gather 的拷贝 kernel 之前（分母是这些区间内的长停顿总时长）。这个结论直接排除了一整类缓解手段——停顿不在 GPU 搬运上（那部分已经单独计过时），而在**发起搬运之前的 host 侧准备**（构造输入列表、事件、分片元数据）。两者要改的地方完全不同。

最后再按**停顿落在哪个区间**聚合一次，区分「是子模块内部的停顿，还是外层框架胶水的停顿」。实测中，长停顿总时长的 94% 落在更外层的胶水里，而不是看起来最重的那个子模块。

## 第 6 步：给出结论

汇总成一张表，每个单元一行：

| 列 | 含义 |
| :--- | :--- |
| 窗口并集 / 真正空闲 | 第 1 步 |
| 每实例 GPU 跨度 / 忙时 / 空闲占比 | 第 2 步 |
| 同流空隙占比 | 第 3 步 |
| 中位 kernel 时长 | 第 4 步 |
| 长停顿的成因 | 第 5 步 |

**写结论时必须分开两类成因**，因为缓解手段不通用：

1. **下发受限**（短 kernel 多）→ 方向是减少 kernel 数量（融合、消除冗余的 dtype 往返）或整段图化。
2. **停滞**（长停顿集中在某一类操作前）→ 方向是消除那个操作的前置准备工作，或干脆去掉那个操作。

把两者混成一句「GPU 利用率低，建议优化」，等于什么都没说。

## 一个容易搞反的因果

不要因为「某个模块空闲占比高」就断定它是瓶颈。空闲占比高只说明**它的计算没有填满自己的窗口**；如果全局空闲的大头在别处，优化它不会有太大收益。

判断顺序是：先看**全局空闲**有多少，再看**这些空闲落在哪**，最后才看某个模块自身的空隙构成。
