# 读数陷阱

每条都写成「现象 → 不知道会得出什么错误结论」。**无法写成后者的条目不该留在这里**——那只是常识，不是坑。

## nsys 报告

### `Proj Time` 是跨度，不是和

`nvtx_gpu_proj_sum` 的 `Total Proj Time` 是区间映射到 GPU 时间轴后的**跨度**（首个到最后一个投影算子之间），不是区间内 kernel 的耗时。

- **不知道会怎样**：把嵌套区间的 `Proj Time` 相加，得到远超墙钟的总数，进而得出「这些阶段互相重叠、可以并行」的错误结论。
- **正确的做法**：要 kernel 时长之和，用 `cuda_gpu_kern_sum:nvtx-name`；它才是可加的。
- 一个可自证的判据：同一窗口内 `:根区间` 的 Proj Time 与 Range Time 近似相等（都接近墙钟），而 kernel 之和只有它们的**一半**。差一倍是常态，不是异常。

### 框架原生区间的名字不在 `text` 列

PyTorch 等框架自己发的 NVTX 区间（通信、`cub::` 调用）把名字放在 `textId` 里，`NVTX_EVENTS.text` 为 NULL。只读 `text` 会整批漏掉。

- **不知道会怎样**：把「最大的 GPU 开销项」漏出报告——单卡下的参数 all-gather 就藏在这批区间里。

### 不能按 kernel 起始时刻落窗归因

用「kernel 的起始时刻落在区间的 CPU 窗口内」来判定归属，看起来直观，但是错的：CPU 提前发射、GPU 执行滞后，短区间会在 GPU 上被整批甩出窗口。

- **不知道会怎样**：某些阶段被数成 0 个 kernel、0 毫秒，于是你把它从优化名单里划掉——而它可能是真正的问题所在。实测中一个只有 4 个 kernel 的短阶段被这样数成了 0。
- **正确的做法**：kernel → `correlationId` → `CUPTI_ACTIVITY_KIND_RUNTIME`（含 `globalTid` 与 CPU 时刻）→ 该时刻该线程上**最内层**的 NVTX 区间。凑巧的是，这正是 nsys 自己采用的规则。
- **不要用同步去修**：清空队列（`synchronize()`、`CUDA_LAUNCH_BLOCKING`）能让窗口与执行对齐，但那改变了被测对象（重叠被破坏、墙钟被拉长），测到的已不是原来那个负载。窗口这个口径直接换掉即可。

### 按执行路径归因时只看最内层

区分两条执行路径的那个区间往往在**栈中间**，不在最内层——最内层是它们共用的子模块名。

- **不知道会怎样**：判不出归属，两条路径的 kernel 混在一起统计，于是得出「两条路径耗时接近」这种无意义的结论。

### 归因合计必须等于 kernel 总时长

按上面的规则汇总，合计应**精确等于** kernel 时长总和，无未匹配项。

- **不知道会怎样**：规则用错时会静默漏掉一部分 kernel，而报告看起来仍然自洽，只是所有占比都偏小。这个等式是唯一能自动发现它的办法。

### CUDA API 条的宽度不是 kernel 耗时

`CUPTI_ACTIVITY_KIND_RUNTIME` 的 `start`/`end` 是**这次调用在 CPU 上的起止**，宽度通常只有几微秒；kernel 的执行时长在另一张表、另一根时钟上。

- **不知道会怎样**：把发射开销读成算子耗时，去优化一个本来不慢的算子；或者反过来，看到 API 条排得密就以为 GPU 很忙。

### 区间名的域前缀

`nsys stats` 显示的区间名是「**域**:区间名」的拼接；sqlite 的 `NVTX_EVENTS.text` 只有区间名，域另存在 `domainId`。默认域渲染为空，于是显示成 `:infer`；框架自己的域会显式出现，如 `CCCL:cub::DeviceSelect::Flagged`。

- **不知道会怎样**：拿显示出来的 `:infer` 去 sqlite 里匹配，一条都查不到，于是以为区间没采到；或者把 `CCCL:` 当成区间名的一部分，做最长前缀匹配时切错边界。

### `Total GPU Ops` 不等于 kernel 数

`nvtx_gpu_proj_sum` 的 `Total GPU Ops` 含 memcpy 与 memset，`cuda_gpu_kern_sum:nvtx-name` 只含 kernel。

- **不知道会怎样**：两个报告的 op 数对不上（实测同一个区间 8640 对 8010），以为归因脚本漏了东西，回头去改一个本来正确的实现。逐项对照时先确认两张表统计的是不是同一批对象。

## 口径混用

### 超出 100% 或为负的占比

- 空闲占比**为负**：拿 CPU 括号的跨度对了 GPU 的 busy 时间。CPU 跑在 GPU 前面时，括号比执行还短。负值是单位不匹配的**信号**，不是数据错误。
- 某类开销**超过 100%**：多半是把父区间直属的 kernel 归给了某一类。父区间里没被子区间覆盖的那部分，装的是「没有单独打点的计算」+「框架开销」，不是纯框架开销。
- **不知道会怎样**：把外层开销算成子模块的锅，优化一个根本不占那么多的地方。

### 逐项求和超过总量

同一层的区间实例在时间上会重叠。各自的跨度**求和**会超过真实墙钟。

- **不知道会怎样**：得出「这个阶段比整个请求还长」的结论，进而怀疑测量本身有问题。
- **正确的做法**：要「这段时间占了多少」就取**并集**；要「累计花了多少」才求和。两个问题的答案不同。

## 数字的稳定性

### 跨运行比较用了 span 类数字

区间跨度、墙钟、空闲率随运行浮动（实测 ±3%）；kernel 归因类数字稳定。

- **不知道会怎样**：把 3% 的浮动读成一次真实的性能变化，于是去改一个本来没问题的东西。
- **正确的做法**：跨运行只比 kernel 归因类数字；引用 span 类数字时带上它出自哪次运行。

### 配置改了却没生效

调用点**显式传入的 kwarg 会覆盖配置文件里的值**。

- **不知道会怎样**：改了配置、跑了实验、发现「没变化」，于是得出「这个参数不影响性能」的错误结论。
- **正确的做法**：测量前确认实际生效的实现，而不是配置文件里写的那个。显式 kwarg、环境变量、缓存的编译产物都会造成这类覆盖。

## 结论层面

### 把「算量占比」当成「时间占比」

FLOPs 少的算子可能因为带宽受限而更慢；零 FLOP 的算子（gather、逐元素、参数搬运）在算量表里根本不存在，却可能占掉可观的时间。

- **不知道会怎样**：按算量排序去找优化点，改的却是一直在等内存的那个。
- **正确的做法**：两者并排呈现，**差距本身是结论**。

### 把单卡的结论外推到多卡

单卡下 all-gather 退化为本地拷贝，占比与多卡完全不同。

- **不知道会怎样**：把「框架搬运占了将近一半」当成多卡下的固有结论，而它其实只是单卡的退化形态。
